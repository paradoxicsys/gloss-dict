Dictionary API /ˈdɪkʃənɛri ˌeɪpiˈaɪ/

Click-to-define endpoint for a test-taking platform, built on the kaikki.org English Wiktionary extract. Every response is pre-built offline; each request is one normalized hashmap lookup plus a byte copy — no database, no per-request parsing.

GET/v1/define/{word}

{word} is exactly what the student clicked, URL-encoded (e.g. Running%2C). The server normalizes it — URL-decode, Unicode NFC, curly quotes to straight, edge punctuation stripped, lowercased — then does one hashmap lookup. A key can resolve to several results: the word's own meanings, plus every lemma it's a known form of, each tagged via.

Open questions for review


        

          
ETag is build-wide, not per-key

          
Every key in one build shares the same ETag (the build version). A redeploy invalidates every client's cache at once, even for words whose content didn't change. Simple, but coarser than per-resource caching — worth a second opinion on whether that's the right tradeoff at scale.

        


        

          
Byte-level dedup in dict.bin measured at 0%

          
Each stored payload embeds its own query field, so two different keys' compressed bytes essentially never match. The dedup mechanism is harmless to keep but isn't earning its keep — real measured savings across 1,568,014 keys: none.

        


        

          
Proper-name form links can surface odd results

          
Clicking "book" also returns Buck [via: alternative of Buck] — a real, verified Wiktionary link (an alternate surname spelling), but low value for a student mid-passage. Open question: drop pos == "name" targets from form/alt-of links, or leave proper-name variants as-is?
